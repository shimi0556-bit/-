# בודק משחקי תלת־ממד

הכלל: **לא מוסרים שינוי בלי לראות אותו עובד.** מודדים במספרים, מסתכלים בצילומים, ובודקים בתנאים שבהם שמעון ראה את הבעיה.

## הקמה
- Playwright עם Chromium. בסביבה הזאת הדפדפן נמצא ב־`/opt/pw-browsers`. לא מתקינים דפדפן חדש.
- WebGL בלי כרטיס מסך אמיתי:
```js
const browser = await chromium.launch({ executablePath: CHROME, args: ['--use-angle=swiftshader', '--enable-unsafe-swiftshader', '--ignore-gpu-blocklist', '--use-gl=angle'] });
```
- **SwiftShader הוא כרטיס מסך מדומה ואיטי מאוד.** זמנים של ציור ושל הכנת שיידרים כאן גדולים פי כמה ממחשב אמיתי. זמני מעבד (JS) קרובים יותר למציאות.
- פותחים את הקובץ הבנוי ישירות: `file:///.../dist/race.html#low`. `#low` מהיר יותר לבדיקה.

## צעדי זמן קבועים (מירוץ של דקה בכמה שניות)
```js
await page.evaluate(() => { const e = window.shimotron.engine; e.stop(); e.quality.dynamicResolution = false;
  window.__step = (dt, render) => { const pr = e.pipeline.render; if (!render) e.pipeline.render = () => {};
    e._last = performance.now() - dt * 1000; e.frame(); e.pipeline.render = pr; }; });
// 150 פריימים בלי ציור = 5 שניות משחק
```
- הנהג של השחקן במצב טייס אוטומטי (`race.setAutopilot(true)`), כך שכל הנהגים נוהגים לבד.
- סופרים חזרות למסלול (respawns), ולכל אחת רושמים את הסיבה: הפוך, רחוק מהמסלול, נתקע, כיוון הפוך.
- **יש הרבה מזל במירוץ של כמה נהגים.** משווים לגרסה הקודמת באותה בדיקה (A/B), ולא מסתפקים בריצה אחת.

## מדידות שכדאי להכיר
- **שלבי טעינה:** `MutationObserver` על הטקסט של מסך הטעינה, עם זמן לכל שינוי (דרך `addInitScript`).
- **פרופיילר מעבד:** בונים גרסה לא מכווצת (`--minify false`), ואז `Profiler.start` ו־`Profiler.stop` דרך CDP. מסכמים זמן עצמי וזמן כולל לפי פונקציה.
- **גודל העולם:** עוברים על הסצנה וסוכמים משולשים ובתים של גאומטריה. זה עוזר להחליט אם כדאי לשמור משהו מראש.
- **ערכי טקסטורה:** מציירים את הטקסטורה ל־RenderTarget מסוג Float, קוראים עם `readRenderTargetPixels` ומחשבים אחוזונים. כך גילינו שהערוץ הכחול במפת נורמלים כמעט קבוע.
- **השוואת נתונים:** נתונים שחושבו מראש מול נתונים שחושבו בזמן ריצה, לפי אזורים (כביש, שוליים, שביל), עם מינימום, מקסימום ואחוזונים.

## צילומים
- `page.screenshot({ path, timeout: 300000 })`, כי פריים ב־SwiftShader יכול לקחת עשרות שניות.
- **מסתכלים על הצילום (Read)** ומתארים מה רואים. בעיה של צבע, כמו רסס אדום, מופיעה רק באי או בשעה המתאימים. מצלמים גם שם.
- מצלמה קבועה לבדיקה: מחליפים את `engine.cameraRig` באובייקט עם `update()` ו־`focusPoint()`.

## בדיקות שחייבים להריץ
1. טעינה עד התפריט, בלי שגיאות (`pageerror` ו־`console.error`).
2. מירוץ קצר בכל סוג שהשתנה: מכוניות, אופנועים, סירות.
3. **לחיצה על "יציאה לדרך" מוקדם**, לפני שהטעינה ברקע נגמרה.
4. גלילה בתפריט: גלגלת מעל הלוח, גלגלת מעל המפה, PageDown, כפתור קפיצה, ומיקום הגלילה אחרי בחירה.
5. צילום תמונה: `page.waitForEvent('download')`, ובדיקה שהקובץ לא ריק. גם בהדמיה של צופה שחוסם הורדות.
6. גרסה בלי אינטרנט: חסימת כל רשת, ובדיקה שאין בקשות.
7. העורך או כל אפליקציה נוספת באותה חבילה.

## מלכודות שכבר נפלנו בהן
- **לולאת המתנה עם `pgrep -f "תבנית"` מוצאת את עצמה** ולא נגמרת. מחכים לקובץ תוצאה, או לתהליך רקע שמודיע כשהוא נגמר.
- **`vite build` מוחק את `dist`** באמצע בדיקה שמשתמשת בו. לא בונים בזמן שבדיקה רצה, או בונים רק מצב שלא מוחק.
- **שתי בדיקות גרפיות במקביל** מאיטות זו את זו עד שצילום נכשל על זמן. מריצים אחת אחרי השנייה.
- **גלילה חלקה ואנימציות** לא מתקדמות כשהמעבד עסוק (למשל בבנייה ברקע). בודקים גלילה אחרי שהטעינה נגמרה, ועם עצירת המנוע.
- פקודה ארוכה מ־10 דקות עוברת לרקע. מריצים אותה ברקע מראש, ומחכים להודעה שהיא נגמרה.

## דיווח
במספרים ובעברית: זמן עד התפריט, כמה נהגים נתקעו לעומת קודם, שגיאות (אין או יש), ומה **לא** נבדק (למשל מחשב אמיתי עם כרטיס מסך, או הצופה האמיתי של claude.ai).

## איך לעשות יותר טוב בפעם הבאה
- תיקיית בדיקות קבועה בפרויקט (`tools/qa/`) במקום סקריפטים חד־פעמיים, עם פקודה אחת שמריצה הכול ומדפיסה טבלה.
- צילומי השוואה אוטומטיים: צילום בסיס, והפרש פיקסלים בין גרסאות.
- מדידה על מחשב אמיתי (Remote או מכונה עם כרטיס מסך) לפני שמבטיחים מספרים.
- בוט שמשחק (נוהג, מחליף מצלמה, מצלם, עוצר) ורושם כל תקלה.
